# VEC-009: Model Registry & Adapter Artifact Verification

**Identifier:** `VEC-009`  
**Category:** Model Registry & Artifact Management  
**Target Systems:** `ModelArtifactsController`, `ModelArtifact` Model, Active Storage, Views (`model_artifacts/index.html.erb`, `model_artifacts/new.html.erb`, `model_artifacts/show.html.erb`)  

---

## 1. Objective

Verify that completed QLoRA training runs can be cataloged into the project's Model Registry as versioned adapter artifacts (e.g. `v1`, `v2`), that adapter weights saved by the Python worker are linked via Active Storage, and that developers can securely download the resulting LoRA adapter files.

---

## 2. Test Cases & Procedures

### TC-009.1: Automatic Version Incrementing
* **Objective:** Verify the new model artifact form auto-suggests the next incremental version tag.
* **Procedure:**
  1. Open `/projects/:project_id/model_artifacts/new?training_run_id=:id`.
  2. Inspect the `Version` field.
* **Expected Result:**
  - If 0 artifacts exist for the project, defaults to `v1`.
  - If 1 artifact exists, defaults to `v2`.

### TC-009.2: Model Artifact Registration
* **Objective:** Ensure a completed run can be registered with a name, version, and description.
* **Procedure:**
  1. Submit POST `/projects/:project_id/model_artifacts` with:
     ```ruby
     {
       model_artifact: {
         name: "customer-support-lora",
         version: "v1",
         description: "Trained on 25 curated helpdesk interactions with Qwen 8B base",
         training_run_id: completed_run.id
       }
     }
     ```
* **Expected Result:**
  - Record created linked to the `TrainingRun`.
  - `artifact.base_model` copied from `training_run.base_model`.
  - Redirected to `/projects/:project_id/model_artifacts/:id` with notice `"Adapter registered."`.

### TC-009.3: Model Registry Index View
* **Objective:** Verify the Model Registry page lists all registered adapters for the project with metadata.
* **Procedure:**
  1. Visit `/projects/:project_id/model_artifacts`.
* **Expected Result:**
  - Table or grid displaying:
    - Display Name (`name + version`).
    - Base Model (`Qwen/Qwen3-8B`).
    - Source Experiment name and link.
    - Creation date and download status.

### TC-009.4: Adapter Artifact File Download
* **Objective:** Verify that attached adapter weights can be downloaded as an attachment.
* **Procedure:**
  1. Attach a mock adapter `.tar.gz` or `.bin` to `training_run.adapter` using Active Storage.
  2. Visit `GET /projects/:project_id/model_artifacts/:id/download`.
* **Expected Result:**
  - Redirects to Active Storage blob path with `disposition: 'attachment'`.
  - Response headers include `Content-Disposition: attachment; filename="..."`.

### TC-009.5: Handling Missing Adapter File
* **Objective:** Verify graceful handling when a registered artifact does not yet have an attached file.
* **Procedure:**
  1. Attempt to download an artifact with no file attached.
* **Expected Result:**
  - Redirects to artifact show page with alert: `"No adapter file available."`.
  - Does not throw a 500 error.

---

## 3. Pass / Fail Acceptance Criteria

- [ ] Artifacts require `name`, `version`, and `base_model`.
- [ ] Version automatically increments (`v1` ➔ `v2`).
- [ ] Download link yields attachment via Active Storage.
- [ ] Missing file generates a clean user alert without exceptions.
- [ ] All tests in `test/models/model_artifact_test.rb` pass.
